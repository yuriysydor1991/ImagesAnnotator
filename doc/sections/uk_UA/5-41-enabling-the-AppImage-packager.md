## Вмикання пакувальника AppImage

Для того щоб увімкнути для побудови ціль `appimage`, що призначена для генерування однофайлового дистрибутиву проекту [AppImage](https://appimage.org/), необхідно сконфігурувати CMake проект з увімкненою змінною `ENABLE_APPIMAGE`:

```
# у кореневому каталозі проекту

cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DCMAKE_INSTALL_PREFIX=/usr -DENABLE_APPIMAGE=ON
```

Наступним чином необхідно побудувати ціль `appimage`:

```
# у кореневому каталозі проекту

cmake --build build --target appimage
```

Скрипт [scripts/build/build-appimage.sh](/scripts/build/build-appimage.sh) виконує обидва кроки за раз, а з переданим прапорцем `--install` встановлює згенерований пакунок у каталог `${HOME}/.local/bin` (дивись [Швидкі скрипти побудови](/doc/sections/uk_UA/5-38-quick-build-scripts.md)):

```
# у кореневому каталозі проекту

scripts/build/build-appimage.sh
```

Файл пакунку генерується у кореневому каталозі побудови проекту. Його назва містить запакований бінарний файл, версію проекту й архітектуру центрального процесора цільової системи, тож із версією проекту `0.12.0` на системі `x86_64` вона є `ImagesAnnotator-0.12.0-x86_64.AppImage`.

Згенерований пакунок є єдиним виконуваним файлом, який взагалі не потребує встановлення:

```
# у кореневому каталозі побудови проекту

chmod +x ImagesAnnotator-0.12.0-x86_64.AppImage

./ImagesAnnotator-0.12.0-x86_64.AppImage
```

### Дві реалізації

Пакунок AppImage пакується генератором CPack `AppImage`, який з'явився у CMake 4.2, щоразу, коли CMake, що виконує конфігурацію, є настільки новим. Старіший CMake натомість лишає окрему ціль, керовану `appimagetool`, яка виконує ту ж роботу самостійно. Крок конфігурації повідомляє, яку саме обрано:

```
-- AppImage packager: the CPack generator
-- AppImage packager: the appimagetool custom target
```

Обидві реалізації генерують той самий пакунок під тією ж назвою і будуються тією ж ціллю `appimage`, отож нічого поза ними - ані наведений вище скрипт, ані конвеєр - не мусить знати, яка з них використовується. `ENABLE_APPIMAGE_CPACK=ON` вимагає саме реалізації CPack незалежно від `ENABLE_APPIMAGE` і завершує конфігурацію помилкою на CMake, старішому за 4.2.

Обидві потребують команди `appimagetool`, а реалізація CPack додатково потребує `patchelf`, яким переписує `RPATH` запакованого бінарного файлу. Дивись [Необов'язкові програми для генерації пакунку AppImage](/doc/sections/uk_UA/3-12-optional-for-the-AppImage-packager.md).

Змінна `CMAKE_INSTALL_PREFIX` кроку конфігурації вище є префіксом, під яким бінарний файл розміщується всередині пакунку, а не каталогом цільової системи, оскільки увесь запакований каталог стає коренем файлової системи запущеного пакунку.

### Файл робочого столу і піктограма

Пакунок AppImage будується навколо файлу робочого столу, який називає піктограму, а цей проект вже встановлює саме таку пару - лаунчер `<ідентифікатор застосунку>.desktop` і піктограму теми `<ідентифікатор застосунку>.png` з [cmake/enablers/template-project-desktop-entry-enabler.cmake](/cmake/enablers/template-project-desktop-entry-enabler.cmake), назви яких узгоджені саме так, як вимагає AppImage. Пакувальник повторно використовує їх, тож пакунок несе той самий лаунчер і ту саму піктограму, що й встановлена копія застосунку, а зміна інструментарію графічного інтерфейсу змінює їх разом з ідентифікатором застосунку (дивись секцію [Розширення](/doc/sections/uk_UA/4-5-extensions.md)).

Побудова лише `ImagesAnnotatorConverter` (`BUILD_IMAGES_ANNOTATOR_CONVERTER_ONLY=ON`, дивись [Виконуваний файл ImagesAnnotatorConverter](/doc/sections/uk_UA/5-40-the-ImagesAnnotatorConverter-binary.md)) не несе лаунчера, оскільки інтеграція з робочим столом належить лише графічному бінарному файлу. Це єдиний випадок, коли пакувальник конфігурує власні файл робочого столу і піктограму з шаблонів каталогу [misc/packagers/appimage](/misc/packagers/appimage), що й дає консольному конвертеру власний пакунок AppImage:

- [appimage.desktop.in](/misc/packagers/appimage/appimage.desktop.in) - файл робочого столу, яким середовища робочого столу інтегрують пакунок;
- [appimage.icon.svg.in](/misc/packagers/appimage/appimage.icon.svg.in) - піктограма, яку називає файл робочого столу.

Реалізація з `appimagetool` додатково конфігурує [appimage.AppRun.in](/misc/packagers/appimage/appimage.AppRun.in) у скрипт запуску `AppRun`, який експортує `LD_LIBRARY_PATH` запакованих бібліотек і запускає бінарний файл проекту. Реалізація CPack натомість генерує власний `AppRun` з файлу робочого столу.

### Змінні кешу

Наступні змінні кешу можливо за бажанням перевизначити для налаштування згенерованого пакунку:

- `TEMPLATE_PROJECT_APPIMAGE_ARCHITECTURE` - архітектура центрального процесора цільової системи (типово: змінна CMake `CMAKE_SYSTEM_PROCESSOR`). Іншими типовими значеннями є `aarch64`, `armhf`, `i686`.
- `TEMPLATE_PROJECT_APPIMAGE_CATEGORIES` - завершений крапкою з комою перелік категорій файлу робочого столу (типово: `Graphics;`).
- `TEMPLATE_PROJECT_APPIMAGE_TERMINAL` - ключ `Terminal` файлу робочого столу (типово: `true`).
- `APPIMAGE_ICON_SRC` - файл-джерело піктограми SVG, який CMake конфігурує поруч з пакунком (типово: наведений вище шаблон).

Останні три описують файл робочого столу, який пакувальник генерує самостійно, тож діють лише для побудови самого конвертера. Графічна побудова бере обидва від активатора лаунчера, де категорії, ключ `Terminal` і піктограма встановленого застосунку оголошені один раз - для застосунку, пакунка DEB, flatpak і AppImage разом.

Архітектура центрального процесора цільової системи потрапляє у назву файлу пакунку і передається `appimagetool` як змінна середовища `ARCH`, яку той вимагає. Її варто перевизначати при крос-компіляції проекту, аби пакунок, який називає CMake, був тим самим пакунком, який вбудовує `appimagetool`.

Детальніше про налаштування пакунку AppImage у файлі [cmake/enablers/packagers/template-project-appimage-general-enabler.cmake](/cmake/enablers/packagers/template-project-appimage-general-enabler.cmake), який визначає усе спільне для двох реалізацій і включає ту, яку обрав - [template-project-appimage-cpack-enabler.cmake](/cmake/enablers/packagers/template-project-appimage-cpack-enabler.cmake) або [template-project-appimage-enabler.cmake](/cmake/enablers/packagers/template-project-appimage-enabler.cmake).

> **Заувага щодо запуску.** На відміну від пакувальників flatpak і snap, які будують проект у власних пісочницях із залежностями, що встановлюють самостійно, `appimagetool` пакує лише встановлений проект. Тож бібліотеки цільової системи, з якими злінковано проект, - зокрема інструментарій графічного інтерфейсу і три бібліотеки ImagesAnnotator - очікуються на машині, де запускається пакунок, якщо тільки проект не встановлює їх у запакований каталог самостійно. Пакунок варто будувати на найстарішому дистрибутиві, на якому він має запускатися, аби вимога бінарного файлу до `glibc` залишалась якомога нижчою.
