# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

- Produce every package this project can generate with a script of its own, adopted from the [cpp-app-template](https://github.com/yuriysydor1991/cpp-app-template.git): [scripts/build/build-deb.sh](/scripts/build/build-deb.sh), [build-flatpak.sh](/scripts/build/build-flatpak.sh), [build-freebsd-pkg.sh](/scripts/build/build-freebsd-pkg.sh), [build-rpm.sh](/scripts/build/build-rpm.sh), [build-snap.sh](/scripts/build/build-snap.sh) and [build-wix.sh](/scripts/build/build-wix.sh) each perform the `Release` configure with a single packager option enabled and then build the one target which produces that package, so a DEB is `scripts/build/build-deb.sh` rather than the configure, the build and the `cpack` invocation spelled out one after another. They accept everything the entry point scripts accept - a `-D<variable>=<value>` of their own lands after the packager option, so `-DUSE_QT6=ON` still chooses the GUI toolkit of the packaged binary - and `--install` installs the package they have just produced with the tool of that packager, which is the new `install_built_package()` helper of [scripts/build/common.sh](/scripts/build/common.sh).

- Install the distribution packages the project is built and run with in a single command, through the new [scripts/packages](/scripts/packages) directory of the same template: [install-debian.sh](/scripts/packages/install-debian.sh) and its Ubuntu named [install-ubuntu.sh](/scripts/packages/install-ubuntu.sh) alias name the compiler, the CMake, the Git, the GTest, the `libcurl` and the nlohmann JSON that a default configure would otherwise fetch and build from their sources, the OpenCV the `ImagesAnnotatorConverter` binary needs the two dataset libraries to have been built with, and the development packages of a **single** GUI toolkit - the default GTKmm3 one, or the `gtkmm4`, the `wxwidgets`, the `qt6` or the `all` named as the only argument, since exactly one of the four is compiled into the binary. The three ImagesAnnotator libraries stay outside of it, no distribution shipping any of them: [misc/ci/install-annotator-libraries.sh](/misc/ci/install-annotator-libraries.sh) remains the step to perform after this one.

- Follow the three ImagesAnnotator libraries to the public class names they carry from now on, and to the installable names those names came with. `LibraryFacade`, `LibraryContext` and `ILib` are gone from all three: the project reaches `iadd::IADataDriversFacade`, `iade::IADataExportersFacade` and `iadi::IADataImportersFacade`, hands the exporters an `iade::IADataExportersContextPtr` and the importers an `iadi::IADataImportersContextPtr`, and names the eighteen dataset layout contexts without the `Library` infix they used to carry - `iade::CocoExportContext` and `iadi::CocoImportContext` rather than `iade::CocoExportLibraryContext` and `iadi::CocoImportLibraryContext`, and so on through the nine layouts of either side. `AnnotatorTypeAliases` follows them with the local aliases the controller instantiates, its own `LibraryContextPtr` and `ImportLibraryContextPtr` becoming `ExportContextPtr` and `ImportContextPtr`. Each library now installs a facade, a context and a library interface header that no other one carries, so the versioned include prefix is no longer what tells three same named headers apart - it stays in use, since it pins the library version every translation unit is talking to and the generic names beside it (`IRecord.h`, `IExporter.h`, `IImporter.h`) are the ones a busy include path collides with.

- Follow the same three libraries to their new installable names, which is one line per library in the enablers and one in each alias header: `ImagesAnnotatorDataDrivers-0.12` with the `ImagesAnnotatorDataDrivers012` namespace, `ImagesAnnotatorDataExporters-0.12` with `ImagesAnnotatorDataExporters012` and `ImagesAnnotatorDataImporters-0.14` with `ImagesAnnotatorDataImporters014`. The packager manifests need no change with it - they build the libraries from the branch the `TEMPLATE_APP_IAD*_GIT_TAG` variables name rather than from a version - and an installation of the previous trio stays on the disk beside the new one, so a checkout of an earlier commit of this project keeps building against it.

- Adopt the `src/app` component decomposition of the [cpp-app-template](https://github.com/yuriysydor1991/cpp-app-template.git) project, whose `app` branch keeps the `IApplication` interface and every descendant of it in an `applications` subdirectory of their own instead of loose beside the classes which create them: `IApplication.h`, `Application`, `ApplicationHelpPrinter` and `ApplicationVersionPrinter` move to `src/app/applications`, and the whole `app::converter` subcomponent - whose `ApplicationConverterComponent` is the fourth descendant of that interface - moves along with them to `src/app/applications/converter`, so that not one implementation of the interface is left outside that directory. What stays at the component root is what drives an application rather than being one: the `ApplicationContext` handed to every `run()`, the `CommandLineParser` which fills it, the `ApplicationFactory` which decides which descendant a command line asks for and the `ApplicationBinaryName.h` the messages name the running binary through. The tests followed the classes they drive - the `UTEST_Application`, `UTEST_ApplicationHelpPrinter`, `UTEST_ApplicationVersionPrinter`, `UTEST_ConversionFormats`, `UTEST_ApplicationFormatsConverter` and `UTEST_ApplicationConverterComponent` suites now live under `src/app/applications/tests/unit`, together with the stand-ins for the moved classes, whose mock directories mirror the new include path the way this project's mocks always do - while the suites of the classes which stayed keep their place under `src/app/tests`. The two mock roots the suites of both halves reach are declared once in `src/app/CMakeLists.txt`: the existing `APP_MOCKS_ROOT` and the new `APPLICATIONS_MOCKS_ROOT` beside it. Nothing of the behaviour changes and no class is renamed - the grouping directory carries no namespace of its own, exactly as in the template, so `app::Application` and `app::converter::ApplicationConverterComponent` keep the names they had - the `#include` paths of the moved headers and the source paths of the CMake files are what this touches, the same 248 test cases pass before and after it, and the single translation unit which tells the two binaries apart is now handed to the main target as `src/app/applications/Application.cpp`. The subcomponent is documented in the new [Implement your own IApplication descendants](/doc/sections/en_US/4-7-implementing-your-onw-IApplication-descendants.md) section, taken from the template along with the decomposition and extended with what this project has and the template has not: the `converter` subdirectory a descendant which is a subcomponent of its own gets, and the `annotator_app_targets_sources()` call which hands a descendant to both binaries against the target file which hands `Application.cpp` to the graphical one alone. The version tracking section was corrected along with it - the configure header it names is `src/project-global-decls.h.in` and not the `src/app/` one it used to say, the very correction the template made in that commit.

- Delete the `${APP_MOCKS_ROOT}/FreeGlutIniter` include directory of the `UTEST_Application` suite, which named a mocks directory this project has never carried: it came in with the [cpp-app-template](https://github.com/yuriysydor1991/cpp-app-template.git) sources, where that stand-in belongs to the `appFreeGlut` branch alone. CMake accepts a non existing include directory without a word, so the line had been compiled over ever since.

- Point the eight entries of the Ukrainian [project structure](/doc/sections/uk_UA/4-project-structure.md) contents at the `uk_UA` sections they name. Six of them addressed the `en_US` file of the same name, so a reader following the Ukrainian contents landed on the English section although the translation was there all along.

- Stamp the binaries with the commit they were configured at again, which the `git commit` line of `--version` had been printing empty. `cmake/enablers/template-project-git-enabler.cmake` asked git for the hash through an `execute_process()` which named no `WORKING_DIRECTORY`, and that call runs in the **binary** directory: a build tree configured outside the checkout - `cmake -B /somewhere/else`, which is what a CI job and a container build usually do - ran `git rev-parse HEAD` where there is no repository, so git failed. Nothing noticed, because the `OUTPUT_VARIABLE` of a command which failed is simply left unset and `project-global-decls.h.in` then configured `project_decls::PROJECT_BUILD_COMMIT` to an empty string. Both queries of that module - the commit hash and the `PROJECT_CURRENT_BRANCH_NAME` the docker image tags are derived from - are asked of `CMAKE_SOURCE_DIR` now, through one `template_project_git_ask()` helper which also reads the `RESULT_VARIABLE`: a git which cannot answer leaves `unknown` behind instead of nothing and the configure says so, passing on what git itself complained about, since that message already names the way out of it. A failure is a legitimate outcome here and stays one - an exported tarball carries no repository at all, a container which bind mounts the sources sees them owned by another user and refuses to read them until that directory is named as a safe one, and a detached HEAD has no branch name to give - but the version printer now says which of those happened instead of printing a blank line.

- Name the nine dataset layouts as a list of formats, in the `Usage` section of both top level READMEs, where the export and the import submenus used to be described by a sentence enumerating them mid paragraph. A reader asking the one question a README is opened with - which formats does this write and read? - now finds the nine as nine bullets, each naming the format first and describing the files it lays down after it, and the two paragraphs which used to repeat that enumeration point at the list instead. The same was done in the READMEs of the [ImagesAnnotator-DataExporters](https://github.com/yuriysydor1991/ImagesAnnotator-DataExporters.git) and the [ImagesAnnotator-DataImporters](https://github.com/yuriysydor1991/ImagesAnnotator-DataImporters.git) libraries, whose layout lists were keyed on the `LibraryContext` descendant implementing each one and now lead with the name of the format that descendant writes or reads.

- Follow the [ImagesAnnotator-DataImporters](https://github.com/yuriysydor1991/ImagesAnnotator-DataImporters.git) library to its `0.13` installable names, which its 0.12.0 release moved away from the `0.11` pair the three libraries had shared: the enabler now probes for the `ImagesAnnotatorDataImporters-0.13` CMake package (the `TEMPLATE_APP_IADI_PACKAGE` default of [cmake/enablers/template-project-ImagesAnnotator-DataImporters-enabler.cmake](/cmake/enablers/template-project-ImagesAnnotator-DataImporters-enabler.cmake)) and `src/annotator-events/events/DataImportersAliases.h` - the single place of the whole project that names the library - includes `<ImagesAnnotatorDataImporters-0.13/LibraryFacade.h>` and aliases `iadi` to the `ImagesAnnotatorDataImporters013` namespace. Nothing else changes: no class, no call and no import behaviour, since the library renamed its installable names alone. A build that still finds a 0.11 installation of the importers now fails at the `find_package()` probe with the name it looked for, instead of compiling against headers which know three dataset layouts while this project drives nine - which is what an installation left behind by an earlier release used to cause in `AnnotatorTypeAliases.h`.

- Convert the annotations formats with a binary which carries no graphical interface at all - the new optional `ImagesAnnotatorConverter` target, built beside the main application out of one and the same code. A machine which only has to turn one dataset layout into another one - a build server, a container image, a data preparation pipeline - had to build and install the whole application for it, GTKmm or Qt6 or wxWidgets included; `-DBUILD_IMAGES_ANNOTATOR_CONVERTER_ONLY=ON` now configures, builds and installs the converter **without a single GUI toolkit present or probed**, and the produced binary loads none. Not one line of the conversion is duplicated for it: every component of `src` is already an object library, and it is now linked into every application target rather than into the named one, through the `annotator_app_targets_link_libraries()` and `annotator_app_targets_sources()` functions of the new `cmake/template-project-annotator-app-targets.cmake` - so a component knows nothing about which binaries a configure produces. Both binaries are entered through the very same `src/main.cpp` and carry the very same `src/app` component, and exactly one translation unit tells them apart: `src/app/Application.cpp`, the class which starts the compiled in `gui::GUIIniter` and is therefore the only thing in the project that names `src/gui` at all. The new `src/ImagesAnnotator-target.cmake` hands it to the main target, while the new `src/ImagesAnnotatorConverter-target.cmake` compiles its own target with the `IMAGES_ANNOTATOR_CONVERTER_ONLY` definition instead - the two target files the `src/CMakeLists.txt` executable declaration was split into, each carrying what differs while the include roots, the `main.cpp` and the install rule they share come from one `annotator_configure_app_target()` call. That definition reaches exactly two sources: `ApplicationFactory`, which then neither includes nor creates the missing class and answers a command line without a conversion with the help message and a non zero status, and the new `src/app/ApplicationBinaryName.h`, through which the help and the version messages name the binary being run. `ENABLE_IMAGES_ANNOTATOR_CONVERTER=OFF` is the mirror case - the main application alone, exactly as before this change - and the conversion stays available through the command line of the main binary in every one of the three. Covered by the new `UTEST_ConverterOnlyApplicationFactory` unit suite, which compiles the factory the way the second binary does and offers it no stand-in for the class that is gone, and by the new `ITEST_*` integration tests - the third kind of test of this project, shell scripts behind the `ENABLE_INTEGRATION_TESTS` option living in `src/tests/integration`, which drive the produced binary the way a user does: they convert real datasets with it and they refuse any GUI toolkit among the libraries it loads and among the symbols it carries, which is the one check no reading of the CMake files could replace. The project dependencies diagram carries the second binary now, and says on it what follows from a binary with no toolkit in it: the OpenCV of the exporters and of the importers libraries, optional for the application whose GUI toolkit implements `IImageCropperFacility` and `IImageSizeFacility` itself, is **required** here - without it this binary writes no PyTorch Vision layout and reads none of the five whose annotations are stored relative to an image size it can then not measure. [The ImagesAnnotatorConverter binary](/doc/sections/en_US/5-40-the-ImagesAnnotatorConverter-binary.md) says the same in prose.

- Run the test suite as a step of the quick build scripts, through the new [scripts/build/debug-test.sh](/scripts/build/debug-test.sh) adapted from the [cpp-app-template](https://github.com/yuriysydor1991/cpp-app-template) this project was started from. It performs the `ctest --output-on-failure` call inside the `build/debug` directory and, like the install step beside it, does nothing at all unless the new `--test` parameter was given, so a plain build stays a plain build. The four `Debug` entry point scripts which build the whole project - [debug.sh](/scripts/build/debug.sh), [debug-clang-tidy.sh](/scripts/build/debug-clang-tidy.sh), [debug-sanitizers.sh](/scripts/build/debug-sanitizers.sh) and [debug-sanitizers-threads.sh](/scripts/build/debug-sanitizers-threads.sh) - chain it in between of their build and install steps, which makes `scripts/build/debug.sh --test` the single command of a configure, a build and a whole test run; the `cppcheck`, the `valgrind` and the `callgrind` ones are left alone, since they build one CMake target the test executables are not a part of. The `--test` parameter joins the `--no-reconfigure` and the `--install` ones in the `filter_script_args()` list of `scripts/build/common.sh`, so it is dropped from what the stage scripts hand over to `cmake` and to `ctest` and every other argument keeps reaching them - `scripts/build/debug-test.sh --test -R "CTEST_FormatsConverter\."` runs a part of the suite inside an already built directory.

- Convert an annotations dataset from one format into another one straight from the command line, through the new `app::converter` subcomponent under `src/app` and the four `--convert-from FORMAT`, `--convert-src PATH`, `--convert-to FORMAT`, `--convert-dst PATH` flags which select it. Until now every reading and every writing of a dataset needed a window, a mouse and a directory chooser, so converting a dataset meant opening it in the application by hand and exporting it by hand - a conversion now fits a script, a `Makefile` and a build pipeline instead, and it starts no graphical interface at all: the run tells what it prepares and what it converts through the log messages alone. Four classes carry it, none of which repeats any import or export logic: `ApplicationFormatsConverter` (implementing the new `IFormatsConverter` interface) submits the import request event of the source format and then the export request event of the destination one over the very pipeline the menu entries drive, so the source is read into the annotations project database the graphical interface edits and that project is what the destination format is written out of; `ConversionFormats` resolves the command line spelling of a format into the `ConversionFormat` enumerator naming it; and `ApplicationConverterComponent`, an `IApplication` descendant beside `ApplicationHelpPrinter` and `ApplicationVersionPrinter`, brings up the event controller and the annotator business controller exactly as `app::Application` does and runs the converter in place of the `gui::GUIIniter`. `ApplicationFactory` creates the two of them together - `create_formats_converter()` builds the converter and `create_formats_converter_application()` hands it to the component - as soon as `ApplicationContext::conversion_requested()` reports all four parameters parsed, which `CommandLineParser` fills in through the `get_params_requiring_data()` mechanism that had stood unused until now, rejecting a half named request instead of silently opening a window. Ten formats may be named on either side of a conversion: the annotations project JSON file of the application itself, read and written through the [ImagesAnnotator-DataDrivers](https://github.com/yuriysydor1991/ImagesAnnotator-DataDrivers.git) library by the existing `AnnotationsDirChanged` and `StoreRequest` events, and the nine dataset layouts of the import and the export submenus. Writing the `pytorch` one cuts the rectangles out of the pictures, so it is the single layout of the ten which reads the pixels of the images rather than their annotations alone: the cutters the four GUI toolkits implement are not there for a conversion, which starts no interface at all, so the request goes out with an empty cropper slot and the [ImagesAnnotator-DataExporters](https://github.com/yuriysydor1991/ImagesAnnotator-DataExporters.git) library fills it with the OpenCV image cropper it ships itself - the very resolution the reading half of a conversion already relies on for the image size reader of the importers library, and the reason `AnnotatorController::handle(Export2PyTorchVisionRequestPtr)` no longer refuses a request carrying no cutter of the interface. That cropper is what the `ENABLE_OPENCV` option of the exporters library builds and that option is `ON` by default, so a stock installation converts into this layout as it does into every other one; an installation built without it carries none, and then that one destination fails with the library saying so. The destination is created when it does not exist yet - the directory for the dataset layouts and the holding directory for the project file - which the graphical interface never had to do, its chooser only ever handing over a directory that is already there. A failing half is what the `DisplayErrorEvent` the annotator controller submits for the interface to show now also reports to the converter, so a conversion that could not read its source or write its destination ends with a non zero exit status. Covered by the `UTEST_ConversionFormats`, `UTEST_ApplicationFormatsConverter` and `UTEST_ApplicationConverterComponent` unit suites - the converter one driving all ten sources and all nine destinations over a mocked event controller to show that every format spelling submits the request event of that very layout - by the conversion cases added to `UTEST_CommandLineParser`, `UTEST_ApplicationHelpPrinter` and `UTEST_ApplicationFactory`, and by the new `CTEST_FormatsConverter` component suite, which runs whole conversions with nothing mocked and asserts on the datasets that ended up on the disk - its `a_native_project_converts_into_a_pytorch_vision_dataset` case being the one which carries a real PNG of its own, since that destination is the one which decodes what it was given, and which skips itself over an installation of the exporters library that ships no cropper.

- Read back **every one of the nine dataset layouts the application exports**, by offering the six the [ImagesAnnotator-DataImporters](https://github.com/yuriysydor1991/ImagesAnnotator-DataImporters.git) library gained - the three Ultralytics YOLO ones, the COCO one, the Pascal VOC one and the Create ML one - as import menu entries of their own in every one of the four GUI toolkits. Until now the import submenu read three layouts against the nine the export one writes, so a project exported into a COCO descriptor or a Pascal VOC devkit could not be brought back; the pair is now symmetric, and a dataset produced by some other tool - the public COCO releases, an Ultralytics training directory, whatever [LabelImg](https://github.com/HumanSignal/labelImg) saved - enters a project for the first time. Six request events carry them through the existing pipeline: `ImportUltralyticsDetectRequest`, `ImportUltralyticsObbRequest`, `ImportUltralyticsSegmentRequest`, `ImportCocoRequest`, `ImportPascalVocRequest` and `ImportCreateMLRequest` with their handler interfaces, the matching `create_ultralytics_{detect,obb,segment}_import_request()`, `create_coco_import_request()`, `create_pascal_voc_import_request()` and `create_createml_import_request()` methods of `EventsFactory`, a `submit()` / `subscribe()` pair each on `IImagesAnnotatorEventController` and its implementation, and six `AnnotatorController::handle()` overloads which reach the library through the very same `handle_import<ContextT>()` template the existing three imports use - the layout is named by the `{UltralyticsDetect,UltralyticsObb,UltralyticsSegment,Coco,PascalVoc,CreateML}ImportLibraryContext` descendant the controller instantiates, so the controller gained no import logic of its own. Every toolkit exposes the six between the YOLO4 entry and the PyTorch Vision one, in the order the export submenu carries the same layouts: the GTKmm3 `Import db` submenu gains six `GtkImageMenuItem`s (with `WindowDataContext` ids, `WindowLoader` getters and `CustomWidgetsFactory` directory choosers of their own), the GTKmm4 one six menu-model items backed by six `Gio::SimpleAction`s and six `GtkFileChooserDialog` shells declared in `GtkmmWindow.ui`, the Qt6 one six `QAction`s built by `add_menu_action()` with `ask_*_import_folder()` choosers, and the wxWidgets one six `ID_IMPORT_*` menu commands with the same choosers. Every one of the new handlers reuses the `handle_folder_import()` helper of its toolkit unchanged, which already carries the directory chooser and the spinner - and, as before, no `has_to_export()` counterpart: an import is what gives the application something to show. Every import request carries the image size reader of the active toolkit as the existing three do, which the three Ultralytics layouts need to place their normalised boxes, and which the COCO and the Pascal VOC ones ignore in favour of the dimensions their own descriptors carry. Covered by six new `CTEST_Importers` component cases driving the controller over dataset directories the suite writes itself - the three Ultralytics ones showing that one and the same box comes back out of the centre and size of a detection line, out of the four corners of an oriented one and out of the polygon of a segmentation one - while the recovered records themselves are covered by the importers library own suites.

- Report only the warnings this project can act on, by handing the GUI toolkit headers to the compiler as system ones. `pkg-config` and `wx-config` publish their directories as plain `-I` paths and the Qt include directories are consumed as plain directories rather than through the imported targets that would have marked them, and a `-I` path is a user directory to the compiler even when it sits under `/usr/include` - so the strict warning set of `cmake/compile-options/template-project-compile-options-GCC.cmake` (`-Wold-style-cast`, `-Wuseless-cast`, `-Wconversion` and the rest) was applied in full to headers no change in this repository can fix. A GTKmm3 build with the tests enabled printed 7994 of them and **not one came from a file of this project**: 811 `-Wold-style-cast` out of the `G_DEFINE_AUTOPTR_CLEANUP_FUNC()` expansions of `glib/gmacros.h`, 189 `-Wuseless-cast` out of `harfbuzz/hb-common.h`, the remainder out of `glibmm`, `sigc++` and the rest of the stack beneath the toolkit. All four GUI enablers now repeat their own `GTKMM_INCLUDE_DIRS` through an `include_directories(SYSTEM ...)` at project scope, before `add_subdirectory(src)`, which demotes exactly those directories into the system include chain for the GUI sources and for every test target that includes the toolkit - the four builds print 7994, 520, 369 and 408 warnings before it and none after. The per-target `target_include_directories()` calls under `src/gui` are deliberately left alone and keep listing the variable, since a directory named by both `-I` and `-isystem` is searched at its system position; and because only the probed toolkit directories are demoted, nothing belonging to this project is silenced - a warning in the project's own sources is reported exactly as before.

- Draw the project dependencies as a diagram of its own, `doc/diagrams/plantuml/dependencies.puml` with its SVG render below the `Usage` section of both top level READMEs. It carries what no prose page had in one place: the three standalone ImagesAnnotator libraries and which of them each other one is built against, the single GUI toolkit compiled in out of the four interchangeable ones, the third party libraries behind each component, and - the point of it - whether every link is `PUBLIC` or `PRIVATE`, since a `PUBLIC` one is the reason this project's own compile sees the data drivers types at all. The two inverted edges are drawn as well: the GUI toolkit implements the `IImageCropperFacility` the exporters library declares and the `IImageSizeFacility` the importers one declares, which is how two libraries that decode no image format reach an imaging stack. The `doc/diagrams/{plantuml,images}` layout is the one both sibling libraries already carry, and both READMEs name the `plantuml -tsvg` command that regenerates the render.

- Read a training dataset back into an annotations project, through the new standalone [ImagesAnnotator-DataImporters](https://github.com/yuriysydor1991/ImagesAnnotator-DataImporters.git) library - the mirror image of the exporters one, made available by the new `cmake/enablers/template-project-ImagesAnnotator-DataImporters-enabler.cmake` (option `ENABLE_IMAGES_ANNOTATOR_DATA_IMPORTERS`, default `ON` since the project no longer builds without it; `TEMPLATE_APP_IADI_PACKAGE` / `TEMPLATE_APP_IADI_GIT` / `TEMPLATE_APP_IADI_GIT_TAG` cache variables), which resolves the library with `find_package()` and propagates it to every project target with `link_libraries()` from before `add_subdirectory(src)`. Three layouts arrive at once - the plain text files, the darknet YOLO v4 training directory and the PyTorch Vision `ImageFolder` layout of cropped out rectangles - so a project exported into any of the three comes back with the annotations it started with, and a dataset produced by some other tool enters a project for the first time. Three request events carry them through the existing pipeline: `ImportPlainTxt2FolderRequest`, `ImportYolo4FolderRequest` and `ImportPyTorchVisionRequest` with their handler interfaces, the matching `create_plain_txt_import_request()`, `create_yolo4_import_request()` and `create_pytorch_vision_import_request()` methods of `EventsFactory`, a `submit()` / `subscribe()` pair each on `IImagesAnnotatorEventController` and its implementation, and three `AnnotatorController::handle()` overloads which reach the library through one new `handle_import<ContextT>()` template - the layout is named by the `{PlainTxt,Yolo4,PyTorch}ImportLibraryContext` descendant the controller instantiates, exactly as the export side names its own. The controller hands the library the very database the project is being edited through, so an import appends to the open project rather than replacing it, the library merge keeps an image the project already holds (which is what makes an import safe to repeat), and a run that recovered anything republishes the images provider so the GUI redraws - the same republication the web page image loader performs. Nothing is written into the directory that is read.

- Offer those three imports as menu entries of their own, in every one of the four GUI toolkits, beside the export ones: the GTKmm3 `Project` menu gains an `Import db` submenu of three `GtkImageMenuItem`s (with `WindowDataContext` ids, `WindowLoader` getters and `CustomWidgetsFactory` directory choosers of their own), the GTKmm4 one an `Import db` menu-model submenu backed by three `Gio::SimpleAction`s and three `GtkFileChooserDialog` shells declared in `GtkmmWindow.ui`, the Qt6 one three `QAction`s built by `add_menu_action()` behind a separator with `ask_{txt,yolo4,pytorch}_import_folder()` choosers, and the wxWidgets one three `ID_IMPORT_*` menu commands with the same choosers. Each toolkit gained an `ImportEventsHandler` beside its `ExportEventsHandler` - created by the `WindowEventHandlersFactory` and registered by `WindowEventsHandler` like every other one - whose three handlers share a `handle_folder_import()` helper carrying the directory chooser and the spinner. It deliberately carries no `has_to_export()` counterpart: an import is what gives the application something to show, so it is offered over an empty project just as much as over a loaded one.

- Implement the image measuring service the imports need in every GUI toolkit: `GtkmmImageSizeProvider` (in `gtkmm-common`, compiled once against whichever GTKmm is active), `QtImageSizeProvider` and `WxImageSizeProvider`, the counterparts of the three image croppers of the export side. The library decodes no image format of its own, and an annotation of the project format is a rectangle in the pixels of its image, so the YOLO v4 layout - whose boxes are stored divided by the size of their image - and the PyTorch Vision one - whose annotation is the cropped image itself - cannot be read back without measuring the pictures. Because the shells are now reused, `WindowOps::run_dialog()` resets each file chooser to its clean per-open state (re-activate the default filter, clear the Save-As name) so a shared instance cannot carry a stale filter or a stale overwrite target into the next open.

Applied to the dialog action buttons (Cancel/Select/Save/Discard/Delete/Load → window-close/object-select/document-save/edit-delete/user-trash/document-open) and, from `WindowLoader::decorate_button_icons()`, to the main-window buttons (open images / DB, zoom in / out, previous / next, delete image / annotation, copy annotation).
